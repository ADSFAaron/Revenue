# 離線行為、資料衝突、權限分級 — 現況與計畫

> 產出於 2026-08-30，分支 `v3`。
> §1–§3 是**現況分析**（已經是這樣，不是計畫）；§4 起是要做的決定。

## 1. Firestore 在斷線時到底做什麼

離線持久化是開著的（`configureFirestore`），所以：

| 操作 | 斷線時 |
|---|---|
| `get()` / `snapshots()` | **可以**，從本機快取回答。查詢也走快取，但只找得到「這台裝置曾經下載過」的文件 |
| `set` / `update` / `delete` | **可以**，排進佇列，回線後自動送出 |
| `FieldValue.increment` | **可以**，而且是**交換律安全的**——多台裝置各自離線加，回線後全部疊上去，不會互相覆蓋 |
| `runTransaction` | **不行**。交易需要先讀伺服器的值，離線直接失敗，也不會排隊 |
| `FieldValue.serverTimestamp()` | 排隊，回線後才決定值。本機快取先看到 null |

**這就是「斷網不能開單」的全部原因**：`submit` 用交易，因為單號
（`counters/{businessDate}.nextOrderNo`）必須是全店唯一遞增的。
交易是唯一能保證兩台機器不撞號的機制，而它正好是唯一離線不能用的寫入。

已經做的（2026-08-30）：首頁橫幅的文案從「新訂單會自動同步」改成事實
（不能開單），收銀台自己多了一條離線提示（首頁橫幅被 push 的路由蓋住），
失敗訊息也改成「沒發到號，籃子還在，回線再送」。

## 2. 差異點清單：離線時哪些資料可能是舊的

app 讀的每一份資料，離線時的來源與風險：

| 資料 | 讀法 | 離線來源 | 舊了會怎樣 |
|---|---|---|---|
| **菜單** `menuRepository.fetchActive` | `get()` | 快取 | **最嚴重**。另一台改了價，這台用舊價開單，而 `OrderLine` 會把價格**永久凍結**在訂單上。錯價會變成歷史事實 |
| **店家設定** `storeRepository.fetch` | `get()` | 快取 | 稅率、營業日切點、付款方式、外送平台抽成都可能是舊的。稅率舊 → 稅額算錯；切點舊 → 記到錯的營業日 |
| **單號** `counters/{date}` | 交易 | 讀不到 | 直接開不了單（§1） |
| **日結** `dailyStats` | `increment` | 佇列 | **不會衝突**。increment 是交換律安全的，多台離線各自累加，回線後總和正確 |
| **訂單本身** | `set` | 佇列 | 單一文件、單一寫入者，不會撞 |
| **報表** `statsRepository.watchRange` | 查詢 | 快取 | 沒下載過的日子**整天消失**，不是顯示 0，是不存在。橫幅有講「顯示這台看過的數字」 |
| **編輯 / 作廢** | 交易 | 讀不到 | 離線做不到。這也順帶擋掉了「兩台同時編輯同一張單導致 `_applyStats` 重複加減」 |
| **時鐘** | 裝置本地 | — | `placedAt` 是裝置時間，`createdAt` 是伺服器時間。兩台時鐘不同步 → 時間軸交錯 |

**要記住的一句話**：目前的架構下，離線**不會產生數字衝突**（因為會衝突的寫入
全都要交易，而交易離線直接擋掉）。代價是離線完全不能收銀。這是一個明確的取捨，
不是漏洞——但如果店裡網路真的不穩，這個取捨要重選。

## 3. 三個選項（要選一個）

**A. 維持現狀 ＋ 誠實提示**（做過，已被 B 取代）
離線只能看、不能開單。零風險，零額外複雜度。

**B. 離線佇列 —— 已實作（2026-08-30）**
離線時把整張單存進本機，回線後自動逐筆送交易、逐筆發號。
- [pending_order.dart](../lib/models/pending_order.dart) — 一張待送出的單。
  存的是**開單當下**的 `placedAt`（不是送出時間）、`OrderLine` 凍結的價格、
  以及**在裝置上先配好的 Firestore 文件 id**。
- [pending_order_queue.dart](../lib/database/pending_order_queue.dart) — 佇列本身：
  `shared_preferences` 持久化、監聽 `connectionStatus`、回線自動 flush、
  一次只跑一輪（`_sending` 旗標）、遇到「還是沒網路」就停下來留著下次。
- [pending_orders.dart](../lib/widgets/pending_orders.dart) — 首頁與收銀台上方的
  「N 筆待送出」列，可以立刻送、可以打開清單逐筆丟掉（打錯的單）。
- 收銀台送出失敗且原因是離線 → 自動入列、清空籃子、告訴使用者。
  **只有新單會入列**；編輯既有訂單需要伺服器上的現況，離線本來就做不到，
  所以照舊回報失敗。

**送兩次的問題怎麼解**：文件 id 在入列時就配好（Firestore 支援離線產生 id），
`orderRepository.submit(orderId:)` 在交易的第一個讀取就檢查該文件是否已存在 ——
存在就直接回傳既有單號、不再發號也不再累加日結。所以「commit 成功但佇列還沒清掉
就被系統殺掉」這種情況，下次 flush 是安全的。

**還沒做、要知道的**：待送出的單**不在報表裡**（它們還不存在於 Firestore），
所以老闆在同步前看到的當日數字會少。目前靠那條橫幅說明，沒有把待送金額
加進當日總計 —— 加進去會讓「畫面數字」和「資料庫數字」是兩回事，暫時不做。

**C. 離線發號**（大工程，不建議現在做）
放棄伺服器配號，改成 `裝置前綴 + 本機序號`，或先寫訂單、單號回線後補。
- 好處：完全離線可用。
- 代價：單號不再連續（稅務/對帳會被問）、要處理補號、要處理兩台重複的
  `orderNo`、要寫對帳畫面。

**選定**：B（2026-08-30 實作）。C 除非要賣給夜市攤商否則不值得。

### 3.1 菜單快取的取捨（已決定：不處理，只提醒）

離線最大的殘留風險不是衝突，是**舊價**：A 機改了價，B 機離線沒收到，
用舊價開單，而 `OrderLine` 會把價格永久凍結在那張單上。

事後對帳不可能（無法分辨「舊價」和「當時就是這個價」），所以**決定不處理**，
只在改價的當下提醒：[store_settings_edit_menu.dart](../lib/settings/store_settings_edit_menu.dart)
存檔後若價格有變，snackbar 會多一行「其他裝置上線後才會拿到新價，一直離線的
收銀機會繼續用舊價」。收銀台的離線提示條也寫明「價格是這台裝置最後看到的」。
責任明確地留在使用者身上：要讓所有裝置定期上線。

## 4. 權限分級

### 4.1 已完成（2026-08-30）：訂單的五分鐘更正窗

- 店員：訂單成立後 **5 分鐘內**可以編輯或作廢；之後要 manager。
- Manager / owner：任何時候、任何訂單。
- 全部人都能**看**所有歷史（不設限，這是刻意的）。

兩邊都擋：UI 在 [store_setting_history_order_detail.dart](../lib/settings/store_setting_history_order_detail.dart)
按 `kStaffCorrectionWindow`（[order.dart](../lib/models/order.dart)）灰掉按鈕並說明還剩多久；
規則在 [firestore.rules](../firestore.rules) 用 `request.time < resource.data.createdAt + duration.value(5,'m')`。
**時鐘是伺服器的**，把裝置時間調回去沒有用。

已知邊界：離線建立的訂單 `createdAt` 要等同步才解析，在那之前店員不能編輯
（畫面會說「還沒存完」）。因為離線本來也編輯不了，所以不構成新的限制。

### 4.2 待做：`dailyStats` 與 `counters` 任何人都能寫

現在的規則是 `allow read, write: if memberOf(storeId)`。拿到任何員工帳號就能
直接改當日總額，而且不留痕跡——比作廢訂單更乾淨，因為 audit log 只記訂單動作。

這是**客戶端 rollup 的固有代價**：日結是收銀端在同一個交易裡累加出來的，
所以收銀端必須有寫入權。三條路：

1. **搬到 Cloud Function**（正解，也最貴）：訂單寫入觸發 `onDocumentWritten`，
   由伺服器累加 `dailyStats`，規則收成 `allow read: if memberOf; allow write: if false`。
   代價：多一次寫入的延遲（收銀畫面的當日數字會慢半秒到一秒）、
   Functions 成本、要處理重試與冪等（用 `orderId` 當去重鍵）。
   `functions/` 專案已經存在（asia-east1），基礎設施是現成的。
2. **規則層限制寫法**：只允許 `increment` 形式的更新、不允許直接賦值。
   Firestore 規則**看不到** `FieldValue.increment` 的語意（收到的是 sentinel），
   所以這條路實際上做不乾淨。**不建議。**
3. **接受並偵測**：保留寫入權，但加一條「日結與訂單加總不符」的對帳檢查
   （設定頁一個按鈕，重算當日訂單並比對）。便宜，抓得到竄改也抓得到 bug。

**建議順序**：先做 3（半天，順便抓得到程式自己的錯），有預算再做 1。

## 5. 時區：`Store.timezone` 存了但沒用

現況：`businessDateOf()` 用**裝置本地時間**減去切點小時再取日期。
`Store.timezone`（預設 `Asia/Taipei`）從來沒有被讀過。

同一家店的裝置都在台灣就不會出事。會出事的情況：
店員手機自動時區跑掉、用網頁版在國外看、之後接外送平台的 webhook（伺服器是 UTC）。
症狀是同一筆單在不同裝置上算出不同的營業日，而且**沒有任何提示**。

三個選項：

1. **存固定 UTC 偏移**（建議）：`Store.utcOffsetMinutes = 480`，
   `businessDateOf` 改成 `placedAt.toUtc().add(offset).subtract(cutoff)`。
   台灣沒有日光節約，固定偏移就是精確解，不需要 tz 資料庫、不增加套件。
   之後要接伺服器端（Functions 算日結、外送平台匯入）時，這是**必要條件**——
   伺服器沒有「裝置本地時間」可用。
2. **上 `timezone` 套件**：完整 IANA 資料庫，日光節約也對。約 500KB 資產，
   對只在台灣營業的店是純成本。有跨時區分店再說。
3. **維持現狀 ＋ 偵測**：裝置偏移和店家偏移不同時跳警告。這其實是 1 的子集，
   做了 1 就順手有了。

**建議**：做 1。改動範圍是 `Store`（加一個欄位）＋ `businessDateOf`（一行）＋
註冊時預設 480 ＋ 設定頁一列。既有訂單不受影響（`businessDate` 是凍結的字串）。

## 6. 還沒排進來的

- ~~編輯舊訂單會套用「現在」的稅率與抽成~~ —— **決定不修**（2026-08-30）。
  稅率不是會常動的東西，為了一個一年可能發生零次的情境增加一個訂單欄位和一條
  分支不划算。留在這裡是為了以後真的改稅率時知道有這回事：改稅率之後去編輯
  舊訂單，那張單的稅會變成新的。
- **Reports 開著跨過營業日切點不會自動換日**：`home.dart` 是 lazy `IndexedStack`，
  頁面 State 整天不重建，`_period` 只在 `initState` 算一次。標籤會自己變成
  「Yesterday」所以不會謊報，但不會自己前進。修法：切點到了發一次 `setState`，
  或頁面 resume 時比對 `currentBusinessDate`。
